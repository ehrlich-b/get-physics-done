### What upstream actually shipped

All 19 commits are one theme plus dependency noise. Read from the diffs, not the messages:

**New capability (2 commits)**
- `e410250c` — **ID-hallucination guard.** `get_abstract` / `search_papers` now prepend a
  natural-language confirmation line naming the returned arXiv ID, title, first author and year,
  and echo back the *queried* ID when it differs. Production traces showed models inventing arXiv
  IDs, getting the canonical paper back, then misreading the mismatch as "cache corrupted" and
  burning 5+ tool calls inventing more IDs. Cache writes happen before the wrapper, so the cache
  stays canonical.
- `d266b529` — **Large-paper read path (RES-1205).** `download_paper` / `read_paper` used to return
  the whole paper inline (~538 KB of single-line JSON for a 456 KB paper), overflowing the desktop
  runtime's 50 KB tool-output cap and forcing a dozens-of-calls chunk-read of an opaque blob. Papers
  over 40 KB now return the saved `.md` path + line count + an 80-line preview. Adds a `read_paper`
  intercept so the search → download → read flow uses the same envelope.

**Bug fixes (4 commits, all real)**
- `56bebddb` — Two genuine bugs. (a) `_try_openalex_search` silently dropped `categories`,
  `date_from`, `date_to` and non-default `sort_by`, so filtered searches returned unfiltered
  results; now fails shut and falls through to upstream MCP. (b) The OpenAlex arXiv institution ID
  was wrong in *both* code paths (`I4210109252` / `I4210168979`), so **OpenAlex search returned
  empty for every call in production**; replaced with the correct source ID `S4306400194`. Also
  fixed `arxiv-replay.py` calling two functions that don't exist, which made the parity gate report
  0% and always fail.
- `4248753e` — Token bucket was a leaky-bucket-of-1: N concurrent callers serialized at
  `(N-1) x 3s`, pushing the 20th caller past the 60 s MCP timeout the bridge exists to dodge. Now a
  real token bucket, capacity 4, refill 1/3 s. Also added response size caps (ar5iv 25 MB, GCS
  100 MB) — previously unbounded buffering.
- `42e27096` — Post-burst waiters stampeded (all computed the same 3 s wait and woke together);
  added a monotonically-advancing `_next_available` deadline. Also fixed
  `_prepend_header_to_result` dropping a leading non-text content block.
- `bcf0a1bf` — Content-type check ran *after* draining up to 100 MB; moved before the stream. And
  the confirmation header was being attached to *error* payloads (upstream returns errors with
  `isError=False`), so it was asserting "canonical paper served" over an error — actively lying to
  the model. Now gated on `_is_success()`.

**Docs (2 commits)** — `fb0aac29`, `1b735681`: docstrings for the coverage gate.

**Dependency bumps (11 commits)** — `arxiv` 3.0.0→4.0.0, `pypdf` 6.12.0→6.12.2, `ruff`
0.15.13→0.15.14, `pytest-asyncio` 1.3.0→1.4.0, plus merge commits.

### What the harness can do now that it couldn't on 2026-06-15

**In this repo:** meaningfully better arXiv literature retrieval — large papers return a path
instead of a 500 KB inline blob, hallucinated paper IDs get called out instead of triggering a
"cache corrupted" spiral, OpenAlex search filters actually apply (and OpenAlex search returns
results at all), and parallel downloads no longer risk the 60 s MCP timeout.

**In practice on this machine: nothing.** This is the finding that matters more than the changelog.

```
installed gpd version (~/.gpd/venv): 1.1.0        # installed 2026-03-15
repo/fork version:                   1.2.2
has arxiv_bridge.py installed:       False
```

`~/.gpd/venv/bin/` contains `gpd-mcp-{conventions,errors,patterns,protocols,skills,state,verification}`
but **no `gpd-mcp-arxiv`**. And `.mcp.json` wires the arXiv server as:

```json
"gpd-arxiv": { "command": "/Users/ehrlich/.gpd/venv/bin/python", "args": ["-m", "arxiv_mcp_server"] }
```

`-m gpd.mcp.servers.*`. The bridge was introduced upstream on 2026-04-07, three weeks *after* your
March 15 install, so 1.1.0 never had it.

So: the entire v36.0 program ran on GPD 1.1.0 with an unwrapped arXiv server, and **merging this
fork changes nothing about what you actually run.** Getting any of the above requires
(a) reinstalling `~/.gpd/venv` from 1.2.2 and (b) repointing `.mcp.json` at
`gpd.mcp.servers.arxiv_bridge`. That's a deliberate action, not a consequence of this sync.

# Phase 64.1 (CORRECTIVE): det_3 generic-norm-consistency fix

**Corrective phase** opened during `/gpd:plan-phase 65`. Phase 65's researcher
flagged that `Der(jordan) != stab(det_3)` in the frozen engine; orchestrator
verification (exact SymPy + Cayley-Hamilton) confirmed a **real bug in the
Phase-64 frozen `det_3`** and pinpointed a one-line fix. This phase applies the
fix in the open and hardens the verification process so it cannot recur.

## The bug

`code/ring_lemma_verification.py` froze the cubic norm with cross term
`2*Re((x1*x2)*x3)`. The **generic (F_4 = Aut(h_3(O))-invariant) norm** of the
frozen Jordan product requires `2*Re((x2*x1)*x3)` (first two octonion factors
transposed). Because octonions are non-associative, `Re(x1 x2 x3) != Re(x2 x1 x3)`
(they differ by the associator), so these are **different cubic forms** — and the
`(x1 x2) x3` form is **not** preserved by `f_4`.

Origin: faithful port of the same factor-order bug in `code/octonion_algebra.py:~2178`
(the Baez-formula implementation). The Phase-64 float-det oracle confirmed the port
matched that source — i.e. it faithfully reproduced the bug.

## Why Phase 64 missed it (the process defect)

The five Phase-64 locks are necessary but **not sufficient** to certify the
F_4-invariant norm:
- `polarize_d(X,X,X) = 6*det_3(X)` holds for **any** cubic form (polarization identity);
- `det_3(diag(a,b,c)) = abc`, `det_3(I) = 1` only constrain the diagonal/identity — the off-diagonal cross term vanishes there;
- the float-det oracle compared against the (already-buggy) `octonion_algebra.py`.

All of these the wrong `(x1 x2) x3` form **also** satisfies. The bug is invisible on
the commutative real subalgebra (diagonal / real off-diagonals) and only bites on
genuinely octonionic points.

## Evidence (exact over Q, orchestrator spikes 2026-05-25)

- `(h_3(O), jordan)` satisfies the Jordan identity → genuine Jordan algebra.
- `f_4 = Der(jordan) = span{[L_a,L_b]}` has dim **52** and reproduces the single-copy
  orbit dimension **24** (= Spin(8) stabilizer, dim 28) — Garibaldi-Guralnick anchor.
  So the inner-derivation **builder is correct**; `det_3` was the wrong object.
- Cayley-Hamilton `X^∘3 − Tr(X) X^∘2 + S(X) X − N(X) I = 0`,
  `S = (1/2)(Tr² − Tr(X∘X))` holds **exactly with `N = N_CH`**, **fails with `N = det_3`(old)**.
- Old `det_3` annihilated by only **30/324** inner derivations; corrected `det_3`
  (= `N_CH`) by **324/324**.
- On the generic point `Xr`: old `det_3 = 24.306164…` (the value the Phase-64 oracle
  recorded); corrected `det_3 = 24.977799…` = float `N_CH`.

## The fix

`code/ring_lemma_verification.py`:
- `det_3()` cross term: `oct_mul(oct_mul(x1, x2), x3)` → `oct_mul(oct_mul(x2, x1), x3)`
  (docstring rewritten to state the generic-norm characterization and the bug history).
- `ASSERT_CONVENTION` header updated: `det3 cross=2Re((x2x1)x3) [generic norm; Phase64.1 fix]`.
- The five existing locks **still pass** (as expected — the bug was invisible to them).

## Permanent generic-norm-consistency lock (Task 7) — the process fix

`jordan_L_matrix`, `inner_derivations`, `octonionic_points`) and two locks in the
harness, **run on genuinely octonionic points**:
- **LOCK 7a**: `det_3 == Cayley-Hamilton generic norm of jordan` at 3 octonionic
  points (the generic norm is unique; this is a complete certificate).
- **LOCK 7b**: `det_3` annihilated by **ALL** inner derivations `[L_a,L_b]`
